# Monday.com 自建协作平台：完整功能地图与开发决策基线

> 用途：本文件是本仓库的冷启动自足文档。任何新会话或新开发者只需阅读本文件，即可理解项目目标、当前状态、monday.com 功能范围、实现难度和下一步决策方式。

## 1. 项目背景与目标

- 团队规模：约 15 人。
- 部署环境：本地局域网，自托管。
- 项目目标：在当前仓库中实现一套参考 monday.com 的团队协作平台。
- 当前阶段：需求选型。先列出 monday.com 的完整核心模块，再由需求方指定哪些优先、哪些延后。
- 重要边界：monday.com 现在是一套 Work OS 产品族，不只是任务看板；其能力覆盖 Work Management、CRM、Dev、Service、自动化、集成、文档、AI 与平台治理。

## 2. 难度口径

以下难度基于“15 人团队、局域网自建、达到稳定可用而非仅做静态界面”估算：

| 标记 | 含义 | 粗略工作量 |
|---|---|---|
| ★ | 简单 | 1～3 天 |
| ★★ | 中等 | 3～7 天 |
| ★★★ | 较难 | 1～3 周 |
| ★★★★ | 复杂 | 3～8 周 |
| ★★★★★ | 平台级 | 需要持续建设 |

工作量会受到技术栈、验收标准、安全要求、外部系统接口和是否需要移动端影响；不可直接把各模块耗时简单相加。

## 4. 当前仓库实现状态

当前实现是早期原型，不应描述为 monday.com 完整核心版本。

已有文件：

- `index.html`：单页界面骨架。
- `styles.css`：看板界面样式。
- `app.js`：前端交互和 API 调用。
- `server.py`：Python 标准库 HTTP 服务和基础 REST API。
- `flowboard.db`：SQLite 共享数据。
- `README.md`：基础启动说明。

当前只覆盖：

| 模块 | 状态 | 说明 |
|---|---|---|
| A02 用户与团队 | 原型 | 仅右上角身份切换，不是真实账户体系 |
| B02 分组管理 | 部分 | 可新增，缺少重命名、排序、删除等 |
| B03 任务管理 | 部分 | 可新增和更新部分字段，缺少完整 CRUD 和批量操作 |
| B06 基础字段 | 部分 | 固定字段，尚无动态字段模型 |
| B13 筛选与排序 | 部分 | 只有搜索和单一状态筛选 |
| B14 任务详情 | 部分 | 有详情和简单字段编辑 |
| D01 任务评论 | 部分 | 支持发表评论，缺少回复、编辑、删除和提及 |
| D07 活动记录 | 基础后端 | 有数据表和接口，前端未完整展示 |
| M01 局域网部署 | 基础 | Python 服务绑定 `0.0.0.0:8080` |
| M04 实时同步 | 未实现 | 当前是 5 秒轮询，不是 WebSocket |

## 5. 建议的技术依赖顺序

以下是模块之间的关键依赖，排期时不宜打乱：

1. A01/A02/A03 用户与权限，是通知、审计、共享和安全的基础。
2. A04/A05 + B01～B06 构成平台核心数据模型。
3. B05 动态字段系统决定筛选、视图、仪表盘、表单、自动化是否可扩展。
4. D01/D05/D07 + M04 构成真正的多人协作体验。
5. C 系列视图依赖稳定的看板、字段、筛选和权限模型。
6. G 自动化依赖统一事件日志、任务队列和动作权限。
7. H 集成依赖 API、Token、Webhook、审计和凭证管理。
8. CRM、Dev、Service 应尽量建立在通用看板平台上，避免各自重复开发数据层。
9. AI 能力应放在稳定数据、权限和审计之后，防止越权读取和不可追踪修改。
