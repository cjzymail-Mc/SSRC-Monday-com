# feature01 · 项目时间管理 + 仪表盘主线冻结基线

> 状态：用户于 2026-08-13 明确要求建立并锁定 feature01 主线。
>
> 用途：约束 feature01 后续需求、原型、技术计划、开发与验收；防止把完整项目管理平台或视觉样图中的临时细节误当成必做范围。
>
> 当前阶段：主线已建立；业务规则与 UX 原型仍在收敛；尚未授权进入正式编码。

## 1. 产品定位

在已交付的 Flowboard 之上，新增一套面向约 15 人鞋类研发团队的**项目时间节点管理与组合仪表盘**。

它首先解决三个问题：

1. 团队能像编辑 Excel 一样快速维护频繁变化的项目节点日期。
2. 单个项目能把六阶段、主线/并行节点和当前日期放在同一条绝对日历轴上理解。
3. 多个项目能在共享日历标尺下横向对齐，让用户快速判断当前阶段、临近节点和轻重缓急；延期历史按需进入轻量复盘。

本 feature 是 Flowboard 上的聚焦能力扩展，不另做独立产品，也不把 Flowboard 扩成完整的企业项目管理套件。

## 2. 目标用户与权限基线

- 主要用户：约 15 人鞋类研发团队，管理跑鞋、篮球鞋、羽毛球鞋等约 10 个并行项目。
- 注册用户：拥有项目时间节点的新增、查看、修改和删除权限。
- 非注册用户：只读查看。
- 本 feature 不做按项目、部门或字段进一步细分的权限模型。
- 权限必须由服务端执行；只在前端隐藏按钮不构成授权控制。

## 3. 统一业务模型

### 3.1 项目生命周期

所有项目严格使用以下六个一级阶段，顺序固定：

```text
创意 → 设计 → 开发 → 测试 → 量产 → 应用迭代
```

本 feature 内不允许用户新增、删除、重命名或调整六阶段顺序。

### 3.2 时间节点

- 每个项目有独立的时间轴和不同的起止日期。
- 一行代表一个任务节点。
- 每个节点必须属于一个项目，并同时具备“项目阶段（一级标签）”和“项目节点（二级标签）”。
- 节点是单个日期上的里程碑，不是有起止日期的任务条。
- 必要业务字段为：`项目名称｜项目阶段｜轨道（主线/并行）｜项目节点｜日期｜时间间隔｜状态｜备注`。
- 主线与并行各自形成独立线性链，共用同一套节点/日期/间隔字段；两轨互不计算间隔、互不顺延。
- 将来可以通过受控变更增加字段，但不能破坏既有数据和导入导出兼容性。

### 3.3 日期、修改历史与轻量复盘

- 日常正式使用一个当前有效【日期】列，不使用计划日期/实际日期双列。
- 每次直接修改和系统级联顺延必须进入修改历史，并能区分直接编辑与自动影响。
- 用户始终只操作一个日期字段；新插入节点第一次保存时，系统无感写入该节点的 `initial_date`。
- 普通用户不能修改 `initial_date`；管理员可在首次录错时通过例外入口纠正，并留下审计。
- 不新增修改原因字段或强制弹窗；解释性信息继续写入既有【备注】列。
- 第一版不建设命名基线、定期快照或复杂版本系统；节点内部保留首次保存的 `initial_date` 与当前 `date`，并复用结构化活动记录中间修改。
- 日常仪表盘不默认展示历史延期天数；延期分析进入一个按需打开、可筛选单项目或多项目的轻量复盘页面。

## 4. 本轮必须交付

### 4.1 类 Excel 时间表编辑器

- 在网页内完成节点表的查看、增加、修改和删除。
- 行列结构明确，支持高频日期调整，降低现有 Flowboard 编辑时间节点的操作成本。
- 支持一个当前有效日期字段的快速编辑。
- 支持按需显示自动计算的时间间隔，并允许通过手改间隔触发受控的后续日期顺延；顺延一直影响到项目末节点，后续各段间隔保持不变，保存后提供一次撤销。
- 日期与间隔采用本次编辑字段优先级：只改谁就以谁为输入；两者同时修改时日期优先，并自动更正间隔。
- 系统内部间隔始终按日期时间链计算；编辑器支持“按日期（默认）/按六阶段分组”两种显示排序，切换排序不得改变日期、间隔或审计数据。
- 主线与并行各自维护独立日期时间链，共用同一【间隔】列；间隔与顺延只在本轨道内生效，两轨互不影响。
- 删除节点不移动其他日期，只重算合并后的相邻间隔。
- 提供清晰的保存、校验、错误反馈和只读状态。
- Excel 作为导入/导出格式；Google 文档不作为数据源或编辑器。

### 4.2 单项目仪表盘

- 展示一个项目的完整六阶段时间轴和全部节点。
- 使用绝对日历标尺和“今天”标记。
- 六阶段拥有稳定且可区分的专属颜色。
- 默认展示当前有效日期，不让普遍存在的历史延期标记淹没日常判断。
- 能识别当前所处阶段/附近节点和延期情况。
- 与该项目的节点清单表形成清晰、可直接编辑的组合体验。

### 4.3 全项目仪表盘

- 支持查看全部项目或多选部分项目。
- 每个项目一条泳道，在共享的绝对日历标尺上横向对齐。
- 用相同的六阶段颜色语义表达各项目进展。
- 红色今日线贯穿所有泳道。
- 默认展示当前有效日期，不让普遍存在的历史延期标记淹没日常判断。
- 支持用户快速识别临近节点、延期项目、当前阶段和轻重缓急。
- 阶段业务顺序固定，但不同阶段日期允许重叠；仪表盘必须真实表达并行状态，不得通过修改日期或混合阶段颜色掩盖重叠。
- 多项目按主线/并行最多显示两条轨道；时间条统一使用 2px 小圆角矩形。

### 4.4 必要配套

- 与 Flowboard 现有登录、权限、活动/审计、备份恢复和部署方式一致。
- 数据迁移前备份且可恢复；不得损坏第一阶段已有数据。
- 覆盖数据层、API、可操作 UI、测试和文档。
- 使用真实或脱敏的代表性项目数据完成用户验收。

## 5. 明确不做

以下内容不进入 feature01 完成条件，除非用户以后明确调整本主线：

- Google Sheets / Google Docs 同步或协同编辑。
- 完整项目管理套件：OKR、工时、预算、资源负载、风险、审批和复杂工作流。
- 项目级细粒度权限。
- 与排期无关的通用版本管理系统；本 feature 仍须保留支撑审计与延期复盘所需的日期变更历史。
- 任意自定义项目阶段、任意阶段顺序或通用工作流引擎。
- AI、CRM、Webhook、表单、SSO、原生 App 等第一阶段冻结主线已排除的产品线。
- 为本 feature 整体重写 Flowboard 或拆成新的独立系统。

## 6. 标准推进主线与阶段门

```text
产品主线冻结
      ↓
业务规则与关键用户旅程确认
      ↓
低成本 UX 原型验证
      ↓
视觉方向确认
      ↓
技术方案、数据与 API 契约
      ↓
纵向切片开发
      ↓
集成测试、视觉收口与真实数据用户验收
      ↓
备份、迁移、部署与运行收口
```

### 阶段门 1：业务规则可实现

进入技术设计前，至少确认：日期顺延规则、状态列语义、编辑器关键操作、仪表盘的判断任务和 Excel 输入输出边界。

### 阶段门 2：原型可用

进入正式编码前，用户应能通过静态原型完成代表性任务，并确认页面结构、交互方式和主要视觉方向。此时确认“避免胶囊化”等方向，不必过早锁死具体圆角、色值和字号像素。

### 阶段门 3：技术方案安全

编码前完成数据模型、API、服务端权限、审计、并发、迁移、备份恢复和旧功能回归策略评审。

### 阶段门 4：纵向切片验收

每个开发检查点必须同时包含数据层、API、可操作 UI、测试和文档。单独完成静态页面、数据库或接口均不算检查点完成。

### 阶段门 5：可上线

真实数据关键旅程、权限、导入导出、日期计算、两类仪表盘、最终视觉人工验收、迁移恢复和第一阶段回归全部通过，才允许进入部署收口。

## 7. UI / UX 决策原则

UI 讨论贯穿全过程，但关注点分层：

1. 原型阶段先确认信息层级、编辑效率、操作反馈和防错。
2. 交互稳定后确认颜色体系、圆角倾向、密度和信息层级等视觉方向。
3. 集成和用户验收阶段基于真实数据集中完成具体色值、圆角、字号、行高、间距和响应式的最终美化收口，不无依据推翻核心交互。

当前静态样图只是验证工具，不是最终视觉规范。用户已明确反馈“条形图圆角过大、太圆、不美观”；下一版必须降低圆角，具体样式继续通过低成本对照样图确认。

## 8. 尚未冻结的设计细节

以下问题必须继续讨论，但不阻止本产品主线成立：

- 六阶段的最终色值。
- 条形粗细、节点点样式、字号、行高和留白（圆角已定为 2px）。
- 轨道字段编辑控件、拖动是否存在、同日排序、完成状态和日常风险提示。
- `状态` 列的枚举和自动/手动语义。
- Flowboard 现有表的复用方式或新增项目/阶段/节点表。
- 多人并发编辑的冲突提示与解决方式。
- Excel 单项目/多项目文件的 Sheet 和列映射契约。
- 全项目仪表盘的排序、筛选和“轻重缓急”计算方式。

这些内容在确认后进入需求验收标准、UX 规范或技术方案；不得只存在于口头上下文。

## 9. 完成边界

feature01 只有在以下结果同时成立时才算完成：

- 用户能以接近 Excel 的效率维护项目节点，无须再靠 Google 文档解决协作编辑。
- 六阶段、轨道、节点、日期和间隔在编辑器及两类仪表盘中共享同一份数据和业务规则。
- 单项目仪表盘能回答“这个项目现在到哪里、下一节点是什么、是否延期”。
- 全项目仪表盘能回答“所有/所选项目今天分别在哪里、谁延期、谁临近关键节点、谁更紧急”。
- 注册用户写权限和非注册用户只读权限均由服务端正确执行。
- Excel 导入导出可承载约定数据且错误可解释。
- 数据迁移、备份恢复、审计、测试、文档和第一阶段回归均通过。
- 本文件“明确不做”的内容没有被擅自纳入。

静态样图通过、某个页面做完或某个接口通过，均不等于整条 feature01 主线完成。

## 10. 纠偏检查

每次制定计划、调整原型、开始检查点或准备验收时回答：

1. 当前工作是否直接提高节点编辑效率或项目时间判断效率？
2. 是否让编辑器、单项目和全项目仪表盘共享同一数据与规则？
3. 是否把尚未确认的样图细节误写成冻结需求？
4. 是否把完整项目管理或其他未来功能偷偷纳入 feature01？
5. 是否省略服务端权限、审计、迁移、备份、恢复或测试？
6. 是否保护第一阶段既有功能和旧数据？
7. 当前成果是否有可操作证据和明确验收标准？

任一答案表明偏离时，先修订需求、原型或计划，再继续。

## 11. 文档优先级

feature01 内发生冲突时按以下顺序处理：

1. 用户最新明确指令。
2. 本文件的产品范围、工程原则和完成边界。
3. `PHASE2_REQUIREMENTS_DRAFT.md` 中用户已明确回答的业务事实。
4. feature01 的当前 `STATE.md`。
5. 后续 UX 规范、技术方案和实施计划。
6. `mockup.html` 等探索性样图。

样图用于提问和验证，不能自行覆盖主线。调整本文件冻结范围须由用户明确拍板。
