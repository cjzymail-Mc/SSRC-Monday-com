# 未来实际部署 ： 硬件要求
-----------

  关于运行速度：.cmd 运行得久，本身不会让系统越来越慢；代码增加也主要影响首次加载和浏览器渲染，不会随运行时间不断累积。

  当前公开前端资源合计约 349KB，在局域网中很小，网速通常不是主要瓶颈。更值得关注的是：

  1. 数据和历史记录增长
     start-gate5-trial.cmd会反复复用 %TEMP%\flowboard-gate5-trial\flowboard-trial.db，不会每次启动重建。项目、节点、审计
     记录越来越多后，首页加载和“最新动态”查询会逐渐变慢。

  2. 浏览器渲染量
     多项目仪表盘会一次渲染很多项目、节点和日期刻度。这部分主要消耗每位用户自己电脑的 CPU，项目越多、时间范围越大，影响
     越明显。

  3. 服务端 CPU和磁盘
     当前服务使用多线程 HTTP Server，SQLite 已启用 WAL 和索引。10–15 人规模基本够用，但大量同时刷新、编辑和实时轮询时，
     服务端 CPU单核性能与 SSD 延迟比内存更关键。

  4. 实时连接
     每个在线页面都有实时事件连接，会周期性查询 SQLite。10–15 人问题不大，但多个重复打开的浏览器标签也会被视为多个连接。

  对你这个规模，建议部署电脑至少采用：

  - 现代 4 核 CPU
  - 16GB 内存（8GB 也能运行，但余量较小）
  - SSD，避免机械硬盘
  - 有线千兆局域网或稳定的 Wi-Fi
  - 禁止服务器自动休眠

  性能影响优先级大致是：

  数据量与页面渲染量
    > 服务端 CPU / SSD
    > 用户电脑 CPU
    > 局域网稳定性
    > 内存容量
    > 纯网络带宽

  如果“运行几小时后变慢，但重启 .cmd 立即恢复”，更像服务端连接或资源没有完全释放；如果重启也不恢复，而换一份较小数据库就
  恢复，主要是数据与历史记录增长；如果只有某一台用户电脑慢，则主要是该电脑的浏览器渲染性能。当前架构可以支撑 10–15 人，
  但正式部署前建议再做一次多用户并发和长期运行测试。

### 8.1 现实中开发此类系统的标准流程

这类「数据编辑 + 时间轴可视化 + 仪表盘」系统，比较稳妥的流程不是先把界面做漂亮，也不是先建数据库，而是依次通过下面的阶段门：

1. **产品主线 / 范围冻结**：确认服务谁、解决什么、不做什么、什么结果算完成。
2. **业务规则与关键用户旅程**：确认项目、阶段、节点、日期、延期、顺延、权限、导入导出的语义；把“用户从进入页面到完成一次工作”的路径走通。
3. **低成本 UX 原型**：用静态 HTML 和假数据确认信息架构、页面布局、操作方式、反馈状态；此时允许快速推翻重来。
4. **视觉方向确认**：在交互基本稳定后，确认颜色体系、紧凑度、圆角倾向、信息层级等方向，形成足以指导开发的视觉基线；不必过早锁死每个像素。
5. **技术方案与数据契约**：决定如何复用 Flowboard、数据表/API/权限/审计/迁移/并发如何实现，并设计 Excel 导入导出契约。
6. **纵向切片开发**：按“数据层 + API + 可操作 UI + 测试 + 文档”逐条交付，而不是先把所有后端或所有 UI 一次性做完。
7. **集成验证、视觉收口与用户验收**：使用接近真实的项目数据，验证编辑效率、日期计算、两类仪表盘、权限、旧功能回归和异常场景；组件行为稳定后统一微调色值、圆角、字号、行高和间距。
8. **部署与运行收口**：迁移前备份、恢复演练、上线检查、使用说明和验收记录。

每个阶段不是完全割裂的，但必须有“够不够清楚，可以进入下一步”的判断。前一阶段发现问题时允许回退，不用为了形式硬往下走。

### 8.2 什么环节讨论 UI 美化？

UI 不是只在最后讨论，应该分成三层：

- **第 3 阶段先谈可用性**：信息放哪里、先看什么、怎么编辑、怎么保存、操作是否容易犯错。这比“漂不漂亮”更早。
- **第 4 阶段确定视觉方向**：颜色体系、圆角倾向、紧凑程度、层级和图形语言在这里确认。当前对“圆角太大”的反馈正属于这一阶段的输入，但暂不需要锁死具体像素。
- **第 7 阶段集中做最终美化收口**：真实数据量和真实浏览器下统一微调色值、圆角、字号、行高和间距；此时不应再随意推翻核心交互。

因此，feature01 当前处于 **第 1 阶段收口 + 第 2/3 阶段并行探索**：现在适合锁定产品主线，也适合继续通过静态样图讨论交互和视觉；还不适合直接进入正式开发。

  关于运行速度：.cmd 运行得久，本身不会让系统越来越慢；代码增加也主要影响首次加载和浏览器渲染，不会随运行时间不断累积。

  当前公开前端资源合计约 349KB，在局域网中很小，网速通常不是主要瓶颈。更值得关注的是：

  1. 数据和历史记录增长
     start-gate5-trial.cmd会反复复用 %TEMP%\flowboard-gate5-trial\flowboard-trial.db，不会每次启动重建。项目、节点、审计
     记录越来越多后，首页加载和“最新动态”查询会逐渐变慢。

  2. 浏览器渲染量
     多项目仪表盘会一次渲染很多项目、节点和日期刻度。这部分主要消耗每位用户自己电脑的 CPU，项目越多、时间范围越大，影响
     越明显。

  3. 服务端 CPU和磁盘
     当前服务使用多线程 HTTP Server，SQLite 已启用 WAL 和索引。10–15 人规模基本够用，但大量同时刷新、编辑和实时轮询时，
     服务端 CPU单核性能与 SSD 延迟比内存更关键。

  4. 实时连接
     每个在线页面都有实时事件连接，会周期性查询 SQLite。10–15 人问题不大，但多个重复打开的浏览器标签也会被视为多个连接。

  对你这个规模，建议部署电脑至少采用：

  - 现代 4 核 CPU
  - 16GB 内存（8GB 也能运行，但余量较小）
  - SSD，避免机械硬盘
  - 有线千兆局域网或稳定的 Wi-Fi
  - 禁止服务器自动休眠

  性能影响优先级大致是：

  数据量与页面渲染量
    > 服务端 CPU / SSD
    > 用户电脑 CPU
    > 局域网稳定性
    > 内存容量
    > 纯网络带宽

  如果“运行几小时后变慢，但重启 .cmd 立即恢复”，更像服务端连接或资源没有完全释放；如果重启也不恢复，而换一份较小数据库就

  # 关于 codex memory // auto-compact

  
• 一句话理解：

  > AGENTS.md 是必须遵守的“公司章程”；STATE.md 是项目进度表；Memory 是 AI 自己整理的“工作笔记”。

  ### OpenAI Codex Memory 怎么工作

  启用后，Codex 会在一次对话闲置或结束后：

  1. 从对话中挑选可能长期有用的信息；
  2. 自动生成摘要、经验、近期输入及证据；
  3. 保存到本机 ~/.codex/memories/；
  4. 在以后的会话中，选择相关记忆作为背景信息提供给模型。

  它不是每次都会立刻记录：太短的会话、仍在进行的会话或额度不足时，都可能跳过或延迟处理。

  OpenAI 没有另外定义一个 .codex/auto-memory/。所谓 auto-memory，可以理解成“Codex 自动提炼和更新 Memory
  的过程”。官方明确建议把这些文件视为自动生成状态，不要以手工编辑它们作为主要管理方式。OpenAI Memories 文档
  (https://learn.chatgpt.com/docs/customization/memories)

  另外：

  - ChatGPT 网页端的 Memory 和本地 Codex Memory 是两套系统。
  - Codex 本地 Memory 默认关闭。
  - 可以分别控制“读取旧记忆”和“把当前对话用于生成新记忆”。
  - /memories 可以控制当前会话，但不会改变全局设置。
  - Memory 不是精确数据库，可能遗漏、过期或判断错误。

  ### 它和 AGENTS.md 的区别

  - AGENTS.md：Codex 每次启动都会读取，适合红线、权限、安全规则、文档真源等必须遵守的内容。
  - Memory：按相关性使用，不保证每次命中，适合偏好、经验、踩坑记录。
  - STATE.md：适合当前阶段、最新状态、下一步等经常变化的信息。

  OpenAI 也明确要求：必须遵守的团队规则应放进 AGENTS.md 或版本库文档，不能只依赖 Memory。OpenAI AGENTS.md 文档
  (https://learn.chatgpt.com/docs/agent-configuration/agents-md)

  ### 还需要维护 Memory 吗？

  需要，但要把“维护”缩小很多：

  - 不用手工维护 Codex 自动生成的 ~/.codex/memories/。
  - 需要维护少量、稳定、跨会话有价值的知识。
  - 项目即时状态、门禁编号、当前进度不要放 Memory，容易过期，应放 STATE.md。
  - 强制规则不要放 Memory，应放 AGENTS.md。
  - 固定施工套路应做成 Skill 或专项文档。
  - Memory 只保留两类：
      - 稳定的用户偏好；
      - 很难从代码重新推导、而且以后还会反复遇到的技术经验。

  你仓库里的 .claude/memory/ 和 .claude/auto-memory/ 属于自己的 Claude 记忆体系，Codex 不会因为目录叫这个名字就自动读取。如果你还会混合使用 Claude 和
  Codex，可以保留一份非常精简、经过审核的共享记忆；如果以后基本只使用原生 Codex，则没有必要继续建设复杂的手工 Memory 流程。

  目前你本机的 Codex Memories 尚未启用。因此我的建议是：

  > AGENTS.md 保宪法，STATE.md 保现状，Skill 保流程；开启 Codex 自动 Memory 负责日常回忆，手工 Memory 只保留极少数长期经验。不要再维护多套互相复制的记忆系
