# 2026-10-13 实战-协作 // 成功迁移到上级网络（xy24）

>>> 我和同事协作开发该repo，我们都是初学者，因此我才打造了这些skill（commit-push-pr 和 sync-main）；日常开发工作中，给我一套推荐的skill使用频率建议和步骤指南

推荐按工作节点使用：**每天开工执行一次 `sync-main`；每完成一个可验证的小改动，执行一次 `commit-push-pr`。提交前不必再单独同步，提交技能会整合远端更新。**

| 场景 | 推荐操作 |
|---|---|
| 每天开工、隔几天重新继续开发 | 执行 `sync-main`，获取同事的新代码 |
| 开发过程中需要同事刚完成的功能 | 再执行一次 `sync-main` |
| 一个小功能或修复完成，相关验证通过 | 执行 `commit-push-pr` |
| 准备提交，但担心远端已有更新 | 直接执行 `commit-push-pr` |
| 同事的 PR 已合并，或通知主线有重要更新 | 在下一次依赖这些改动前执行 `sync-main` |
| 工作未完成，准备下班 | 保留本地改动，下一次继续；不必为了下班而提交 |

你们日常可以照着下面的步骤走：

1. **开工同步。**  
   调用 `$sync-main`，等它确认同步完成。若报告仍有阻塞，先处理清楚，再开始新改动。

2. **约定各自负责的内容。**  
   简单说明“我今天改哪项功能、主要涉及哪些文件”。尽量避免两个人同时大改同一个文件。

3. **完成一个小而完整的改动。**  
   例如一次修复一个问题，或完成一个能单独验证的功能。让 agent 做与改动相关的检查，并复用已经有效的测试结果。

4. **提交并推送。**  
   调用 `$commit-push-pr`。它会检查改动、整合远端更新、处理普通冲突、验证并推送。**默认提交当前全部符合条件的改动**；若只想提交部分内容，调用时明确限定范围。

5. **确认结果并通知同事。**  
   技能会报告提交或 PR 的链接。若直接推送 `main`，同事执行 `sync-main` 即可获取；若生成 PR，需要审查并合并后，才能通过 `sync-main` 获取。

两条规则尤其值得记住：

- **技能报冲突时，继续在同一聊天处理。**普通冲突应由 agent 完成恢复；涉及“两个功能到底应如何取舍”的冲突，需要你们决定。提交失败后保留现场，让 agent 续接处理。
- **代码同步与部署分开。**这两个技能处理开发仓库的 Git 工作；最终部署电脑的更新，需要另行执行你们约定的部署流程，真实数据库也不随 Git 同步。

对你们目前的协作规模，通常就是：**开工同步一次 → 开发并验证 → 完成一个小任务就提交 → 同事按需同步。** 不需要每改一个文件就执行技能，也不需要每次同步都跑完整测试。
